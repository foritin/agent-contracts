公共规范边界、来源与查漏补缺

1. 自包含承诺

本目录的 HTML 页面是公共层的执行性规范：实现者不需要打开当前 R-Code 源码、
small-rust-hermes 源码或任何根目录 Markdown，便可建立公共 crate、完成接口设计、
编写测试并接入两个产品。

文中出现的“来源路径”仅用于解释本规范如何从现有产品抽取事实；它们不是运行时或文档依赖。
离线打包时路径不存在不影响任何实现步骤。

2. 逻辑模块与物理 crate 的区别

当前两个项目将部分能力内聚在同一模块内。例如 Tiny Hermes 的 hermes-core 内含错误和
上下文压缩，hermes-llm 内含配置；而 R-Code 将契约、持久化与 IPC 分散到 TypeScript
packages。为避免把现状误读为唯一正确的 crate 切分，本规范采用两层表达：

逻辑能力必须存在的合同可以的物理位置
消息 / Provider / ToolHosttrait、DTO、stream 语义hermes-core 或多个小 crate
会话 / 文档 IOappend、恢复、原子写hermes-store 或产品 store
compaction / error / config安全默认值、审计、错误分类core / llm / 独立 crate
MCPserver 生命周期、命名空间、错误映射hermes-mcp
IPC / desktop shell版本握手、请求与事件边界仅需要桌面进程者实现

只要公开合同和兼容性政策不变，物理拆分可以在发布窗口内调整；不要为了和旧目录同名而牺牲
依赖方向。

4. 本轮补齐的缺口

初始资料已描述接口和 crate 映射，但对“如何让两端长期共享而不漂移”覆盖不足。本目录新增并
固定了以下内容：

  1. 子模块与 pin 策略：公共规范/实现可独立建仓，产品只升级经审查的 commit。
  2. 双消费者验收向量：不以单端编译通过替代合同验证。
  3. 版本语义：明确何时是 patch、minor、major，特别是权限默认值与事件顺序。
  4. 数据兼容性：为 JSONL、配置、IPC 和 ToolSpec 规定未知字段与迁移策略。
  5. 故障演练：取消、坏尾行、MCP 断开、坏配置、秘密泄漏均是发布前硬门。

5. 实施者的阅读路径

第一次从零实现时按下面顺序阅读即可：

  1. 00-overview：确定边界和依赖图。
  2. 04-message-types、01-llm-provider、03-tool-host：先冻结核心 DTO 与 trait。
  3. 02-session-management、07-error-handling、08-config-management：建立可恢复的
    基础设施。
  4. 05-mcp-client、06-compaction：完成真实 Agent 所需的扩展能力。
  5. 09-ipc-transport、10-tauri-shell：只在有独立桌面 / worker 进程时采用。
  6. 12-api-contracts、13-submodule-and-workspace-integration、14-common-quality-gates：
    将接口变成可执行的双端合同。

完成后再进入 ../r-code/index.html 或 ../tiny-hermes/index.html 的产品私有
阶段。即使公共目录以 vendor submodule 的形式嵌入，该阅读顺序不变。

本页为可离线浏览的重构规范；代码示例是实现合同，不是已交付源码。
