公共模块作为子模块：集成合同

1. 本文的定位

agent-core 是 Charter 与 Tiny Hermes 的共同重构规范包。它不是某一端应用的
实现，也不携带产品私有功能；它定义两端必须保持一致的消息、Provider、会话、工具、MCP、
压缩、配置、错误和进程通信合同。

本目录可以独立建仓并以 Git submodule 固定到两个目标仓库。这样做的目的不是让两个产品
共享一个不受约束的代码目录，而是让它们共享一份可版本化、可审查、可验证的公共边界。

本交付物仅包含重构文档。实现团队应按本文档在自己的 Rust workspace 中创建 crate；
不能把文档中的建议性目录当成已经存在的库。

2. 可打包目录合同

将下列三个目录放到同一个父目录后，任意一个 index.html 都应可离线打开：

text
rebuild-kit/
├── agent-core/          # 本目录：公共合同与集成顺序
├── r-code/         # R-Code（Charter）特有产品与实现说明
└── tiny-hermes/     # Tiny Hermes 特有产品与实现说明

跨目录链接以这三个目录同级为前提。每个目录本身也有完整的入口、目录、代码示例、
验收项和来源说明；即使暂时不打开另两个目录，也不会缺少本项目的执行步骤。

3. 推荐的 Git 布局

公共规范仓库和两个实现仓库分别拥有版本号。实现仓库只固定公共规范的 commit，不直接跟随
main，以保证一次发布所依据的合同可重现。

bash
# 在 R-Code（Charter）或 Tiny Hermes 的重构仓库根目录执行
git submodule add <public-docs-or-contract-repo> vendor/agent-core
git submodule update --init --recursive

# 升级时必须显式审查差异，并在产品仓库中提交新的 gitlink
git -C vendor/agent-core fetch --tags
git -C vendor/agent-core checkout <reviewed-tag-or-commit>
git add vendor/agent-core .gitmodules
git commit -m "docs: pin agent-core contract <version>"

如果团队将公共 crate 与公共规范放在同一仓库，建议保持两层目录：

text
vendor/agent-core/
├── docs/                    # 本文档站导出物
└── crates/                  # 后续实现团队建立的公共 crate

这能避免让应用层依赖文档相对路径，也能让文档独立打包时不携带业务源码。

4. Cargo workspace 接入规则

目标项目应通过 workspace dependency 名称引用公共 crate，业务 crate 不得互相穿透私有模块。
下面示例是目标结构，而非现有文件：

toml
# Cargo.toml（R-Code（Charter）或 Tiny Hermes 根目录）
[workspace]
resolver = "2"
members = ["crates/*"]

[workspace.dependencies]
rebuild-core = { path = "vendor/agent-core/crates/hermes-core" }
rebuild-llm = { path = "vendor/agent-core/crates/hermes-llm" }
rebuild-mcp = { path = "vendor/agent-core/crates/hermes-mcp" }
rebuild-store = { path = "vendor/agent-core/crates/hermes-store" }
toml
# crates/charter-agent/Cargo.toml（同样适用于 Hermes 私有 crate）
[dependencies]
rebuild-core = { workspace = true }
rebuild-llm = { workspace = true }

必须遵守：

  1. 公共 crate 不依赖 charter-*、hermes-* 私有 crate，也不依赖 UI、IM 或桌面框架。
  2. 公共类型只使用稳定的语义版本合同；破坏字段语义、枚举含义、流式事件顺序或权限默认值
    都是破坏性变更。
  3. 应用层只通过公开 trait / DTO 集成，不读取公共 crate 的内部持久化细节。
  4. 若某一端需要扩展字段，优先使用显式版本化的 metadata 或新增 DTO 版本；不得让另一个
    项目被迫理解它的私有状态。

5. 采用顺序

公共层应先于产品私有层落地，且每一步都有可以独立运行的验收：

顺序公共能力最小验收后续消费者
P0错误、消息与 Session 模型serde 往返、未知字段策略、崩溃后可读取 JSONL两端所有 crate
P1Provider trait 与一个 mock provider流式文本、工具调用、取消、usage 事件可录制Charter Agent、Hermes turn
P2ToolHost 与 MCP host工具命名、失败默认、MCP stdio/HTTP 断开恢复Charter Gateway、Hermes tools
P3配置、秘密与 compaction配置优先级、敏感值不打印、长对话摘要不丢关联两端入口
P4IPC / Tauri 外壳（仅需要者）请求、事件、版本不兼容拒绝、窗口重启恢复Charter 主进程、Hermes GUI

每一个 P 阶段都应先由两个消费者各写一组契约测试，再允许下一个阶段开始。这样可以避免
公共层在只满足一个产品时过早冻结。

6. 版本与兼容性政策

变更版本策略必需动作
文档措辞、示例、实现细节不改变合同patch链接和示例编译检查
新增可选字段、可选 trait 方法、可选事件minor两端旧消费者回归测试
删除/重命名字段、改变默认权限、改变事件顺序major写迁移说明、双端同时升级、灰度回滚方案
修复安全漏洞立即 patch 或 major说明风险、最小安全版本、升级截止时间

建议在两个目标仓库各维护一个 contract-lock.json，记录公共规范 commit、公共 crate 版本和
验证结果：

json
{
  "publicContract": "v0.4.0",
  "commit": "<immutable-commit>",
  "validatedBy": {
    "charter": "cargo test -p charter-contract-tests",
    "tinyHermes": "cargo test -p hermes-contract-tests"
  }
}

7. 跨项目契约测试

公共合同不能只靠 API 签名验证。每次 pin 或升级至少运行下表场景：

合同Charter 侧证据Tiny Hermes 侧证据
ContentBlock / 工具结果配对Agent 取消时不留下孤儿 tool_userun_turn 取消后可再次请求 Provider
Provider streamUI 可显示增量、usage 和错误CLI、HTTP、IM 都消费同一事件顺序
ToolHost 失败默认未知工具进入审批 / 拒绝未知或未注入工具不能静默执行
Session 持久化重启后任务事件可投影JSONL 会话可恢复、可被反思读取
MCP 命名外部工具不碰撞 Gateway 名称<server>__<tool> 可路由到正确 server
配置与秘密诊断包不含 tokenconfig.toml 和 channel 凭据权限受限

8. 故障处理与退出条件

发现公共合同缺陷时，不要在某一产品内临时复制修复。正确流程是：

  1. 记录最小复现与受影响的合同编号。
  2. 在 agent-core 中修正文档、版本规则和测试向量。
  3. 两端用同一向量复测；任何一端不能通过时保持旧 pin。
  4. 仅当两端均提供通过证据，才更新 submodule 引用。

本阶段完成的定义：两个项目可以在不读取当前 Charter 或 small-rust-hermes 源码的条件下，
仅凭本目录的 HTML 文档创建一致的公共接口、测试夹具和版本治理流程。

本页为可离线浏览的重构规范；代码示例是实现合同，不是已交付源码。
